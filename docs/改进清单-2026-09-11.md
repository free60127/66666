## 一、P0 — 建议立刻修（2 条）

### S1. 任意网页可窃取服务端配置的 `AI_API_KEY`（已实测复现）

**证据**：`server/index.mjs:508`（`Access-Control-Allow-Origin: *`）、`:566/:596/:635/:667`（`baseUrl` 取自请求体）、`:568/:598/:637/:669`（`apiKey = body.apiKey || process.env.AI_API_KEY`）、`:278-282`（把该 key 作为 `Authorization` 发给 `baseUrl`）

**现象**（实测输出，见附录）：
```
① OPTIONS /api/analyze  Origin: https://evil.example  → 204  Access-Control-Allow-Origin: *
② POST  /api/analyze    （不带 apiKey，baseUrl 指向攻击者）→ HTTP 200
③ 攻击者服务器收到： POST /v1/chat/completions
                    Authorization: Bearer sk-VICTIM-REAL-KEY-9f3a   ← 服务端自己的 key
```

**影响**：
- 任何网页都能让用户**本机正在运行的后端**（默认 8787）把 `.env` 里的 key 明文发到攻击者服务器；用户只要开着服务逛任意网站即可被窃取。
- 线上实例目前 `hasKey:false`（未配置环境变量 key，已核实），**该攻击面尚未激活**；但 `render.yaml` 明确支持配置 `AI_API_KEY`（`sync: false`），一旦配上就立即暴露。
- 即使没有服务端 key，`baseUrl` 任意可控 + 无鉴权 + 无频率限制，也等于把服务端当成**开放代理**（SSRF：可探测内网/云元数据地址 `169.254.169.254`）。

**修法**（三选一或组合，建议全做）：
1. `baseUrl` / `apiKey` 一律不信任请求体，只读服务端环境变量（多人共用场景改为"自带 key 必须显式开启"的白名单开关）。
2. 若必须允许前端传 key：禁止客户端传 `baseUrl`；对 `baseUrl` 做协议 + 主机白名单校验，拒绝私网/环回/链路本地地址。
3. CORS 收紧为同源（或 `ALLOW_ORIGIN` 环境变量白名单），`/api/*` 加最小限流（按 IP 令牌桶）。

### S2. 结果数据未做元素级校验 + 无 ErrorBoundary → 白屏且用户无法自救

**证据**：`src/App.jsx:1098`（`const sentences = result.sentences || []`）、`:1442`、`:1509`（`sentences.flatMap((s) => s.findings || [])`、`s.findings`）、`server/index.mjs:348`（服务端只做 `Array.isArray(parsed.sentences)`，元素原样透传）、`src/App.jsx:478-505`（`#job=` 恢复路径）、`src/main.jsx`（无 ErrorBoundary，全仓库 0 处）

**现象**：模型只要返回 `sentences: [null, {...}]`，渲染期即 `TypeError: Cannot read properties of null`；没有 ErrorBoundary，React 卸载整棵树 → 整页白屏。更糟的是恢复入口本身是崩溃路径：URL 上的 `#job=` 会把**同一份坏数据**再灌回 `result`，用户 F5 继续白屏，只能手动清 localStorage 或删 hash。

**修法**：① 入口统一归一化 `(Array.isArray(x) ? x : []).filter(v => v && typeof v === 'object')`；② `main.jsx` 外挂 ErrorBoundary，兜底页提供"清除本机缓存"按钮；③ 服务端对 `sentences/overall/vocabularyNotes` 做元素级 shape 校验后再落库。
